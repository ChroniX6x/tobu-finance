# Review-Nacharbeit: sichere Migrationen

Die Review-Punkte wurden im bestehenden Feature-Branch bearbeitet. Auf Nutzeranweisung werden sie dieses Mal nicht in separate PRs ausgelagert. Die vom Nutzer zuvor ausdrücklich gewünschten Browser-Zeitbudgets, Parallelität und Videos bleiben bestehen.

| Anmerkung | Ergebnis |
| --- | --- |
| Formatierung | Die API-/Root-Dateien folgen der aufgelösten Prettier-Konfiguration (vier Spaces, einfache Quotes). Im Web gelten andere Prettier-Voreinstellungen; `wizard.spec.ts` besteht die Prüfung einschließlich Abschluss-Newline bereits. `playwright.config.ts` wurde ohne Verhaltensänderung an seine aufgelöste Konfiguration angepasst. Keine historischen Commits umgeschrieben. |
| Timeouts/Trace | Die ausdrücklich angeforderten 60 Sekunden Test- und 15 Sekunden Assertion-Budget sowie Trace bleiben erhalten. Kein erneutes Erhöhen, kein Abschalten von Videos/Parallelität und keine zusätzlichen Retries. Die Nutzerentscheidung ist bereits in `development.md` dokumentiert. |
| `/health/migrations` | Fehler werden wie bei `/ready` mit 503 und neutralem Status beantwortet. Ein echter Integrationstest erzeugt inkonsistente Historie und prüft die Antwort sowie anschließende Erholung. |
| DB-Abfrage pro API-Request | Gleichzeitige Prüfungen teilen sich eine laufende Abfrage; ein erkannter Lock wird eine Sekunde konservativ gecacht. **Kein Cache für „nicht gesperrt“**: Sonst könnten Requests nach einer neuen Sperre noch kurz zugelassen werden. Einzelne aufeinanderfolgende Requests im Normalbetrieb behalten deshalb die DB-Prüfung. Fehler werden nicht gecacht. Writer müssen weiterhin vor Migrationen gestoppt/drainiert werden. |
| CLI-Fehler | Ein eigener `MigrationDiagnosticError` markiert Meldungen aus vertrauenswürdigem Runner-Code. Die CLI zeigt diese und entsprechend markierte Ursachen an; normale Fehler, gefälschte Fehlernamen und rohe Treiberursachen bleiben unterdrückt. Auch URI-Parsing und fehlende Konfiguration liegen nun im geschützten CLI-Fehlerpfad. |
| Lock vor Preflight | `plan()` prüft die Namespaces ausgewählter transaktionaler Migrationen vor jedem Lock. Fehlende Collections und veraltete Bestätigungen lassen keine Sperre zurück. Nach Lock-Erwerb bleibt die erneute Prüfung gegen zwischenzeitliche Änderungen erhalten; Fehler **nach** Erwerb erfordern weiterhin sichere Recovery. Ein vorhandener Recovery-Lock blockiert die Plananzeige nicht wegen fehlender Namespaces. |
| Doppelter Image-Pin | Docker-Orchestrierung und kompilierter Backup-Helper lesen `apps/api/src/database/runtime-defaults.json`. Der Build nimmt die JSON-Datei ins Artefakt auf. Der Workspace-Check erzwingt weiterhin einen konkreten Versionspin und Übereinstimmung mit Compose; zusätzlicher Tooling-Test vorhanden. MongoDB bleibt 9.0.4. |
| Import-Regex | TypeScript-AST statt Textregex. Kommentare und Strings mit `import`/`require` werden zugelassen; Runtime-Imports, dynamische Imports, Require-Aufrufe, Import-Aliase und Runtime-Reexports bleiben gesperrt. Typ-Imports bleiben erlaubt. Das ist weiter eine Regel für vertrauenswürdigen Projektcode, keine Sicherheits-Sandbox. |
| Tote Pfade/Kosmetik | Alter `workspace migrate`-Pfad und die zugehörige Dev-CLI-Abzweigung entfernt. Aktive `db:migrate`-Befehle bleiben unverändert. Überschrift korrigiert; `.gitignore` ignoriert `/backups/` ausdrücklich im Root. |

Nachweise: acht API-Unit- und acht Tooling-Tests erfolgreich. 38 Integrationsprüfungen auf einer ausdrücklich isolierten nativen MongoDB-8.2-Testinstanz erfolgreich, einschließlich realer HTTP-/Datenbankfehler und Recovery. Diese Zusatzprüfung ändert den Docker-Pin nicht und ersetzt keinen neuen Docker-9.0.4-/CI-Lauf. API-Build, ESLint, Prettier, Vertrags- und Workspace-Prüfung gehören zur lokalen Abschlusskontrolle. Auf dem Docker-Rechner danach `npm run quality:full` für den neuen Commit ausführen; frühere erfolgreiche Gates gelten nicht automatisch für diese Nacharbeit.
